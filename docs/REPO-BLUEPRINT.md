## Section 5: Naming and Convention Notes

### Naming Table

| Construct | Convention | Example |
|-----------|-----------|---------|
| React components | PascalCase | ListingCard, EcoScoreCard |
| Variables and functions | camelCase | createListing, incrementPoints |
| Boolean variables | is/has/should/can prefix | isLoading, hasSession, canDelete |
| Interfaces and Types | PascalCase | ListingRow, ScanResult, BadgeType |
| Constants | UPPER_SNAKE_CASE | MAX_SCAN_PER_MINUTE, ECO_POINTS_PER_LISTING |
| Custom hooks | camelCase with use prefix | useSupabase, useScanHistory |
| CSS classes | kebab-case Tailwind utilities | eco-card, scan-result |
| Route segments | kebab-case | /listings/[id], /auth/callback |
| DB tables | snake_case | collection_points, eco_actions |

### Server Actions Pattern

All files in actions/ must begin with the use server directive. Every action returns
{ data: T | null, error: string | null }. Input is validated with Zod before any DB call.

    // actions/listings.ts
    import { ListingSchema } from @/lib/validators/listing
    import { createServerClient } from @/lib/supabase/server

    export async function createListing(formData: FormData) {
      // 1. Parse + validate with Zod
      // 2. Auth check via supabase server client
      // 3. AI moderate before insert
      // 4. Insert via supabase (never direct SDK in components)
      // 5. Increment eco_points via RPC
      // 6. Return { data, error }
    }

### Zod Validators

Each entity gets its own file under lib/validators/:
- lib/validators/listing.ts    exports ListingSchema and inferred ListingInput type
- lib/validators/scan.ts       exports ScanResultSchema and ScanResult type
- lib/validators/collection-point.ts  exports CollectionPointSchema and CollectionPointInput
- lib/validators/profile.ts    exports ProfileSchema and ProfileUpdateInput

### Supabase Access Rule CRITICAL

Never import from @supabase/supabase-js directly in page/component files.
Always use the three wrappers:

| File | When to use |
|------|-------------|
| lib/supabase/client.ts | Client Components only use client |
| lib/supabase/server.ts | Server Components, Server Actions, Route Handlers |
| lib/supabase/admin.ts | Admin operations only -- import only from actions/admin.ts or cron routes |

### File Size Constraint

- Hard cap: 800 lines per file
- Target: 200-400 lines
- If a file reaches 600 lines during development, extract a sub-module immediately
- High-risk files: actions/listings.ts, components/listings/ListingForm.tsx
- SQL migration files are exempt from line cap -- split by migration file number instead

### Leaflet Dynamic Import

All components under components/map/ must be loaded via next/dynamic with ssr: false:

    // app/(app)/map/page.tsx
    import dynamic from next/dynamic
    import { PageSkeleton } from @/components/shared/PageSkeleton

    const MapContainer = dynamic(
      () => import(@/components/map/MapContainer),
      { ssr: false, loading: () => <PageSkeleton /> }
    )
